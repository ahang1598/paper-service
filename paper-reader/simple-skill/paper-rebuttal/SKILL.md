# 论文答辩回复

收到审稿意见后，目标是解决真正影响评分的顾虑，不是逐条平均用力地辩护。

## 获取论文与审稿意见

**functionName**: `AcademicPaperSearch`

**parameters**:

```json
{
  "type": "object",
  "properties": {
    "query": {
      "description": "论文文件或审稿意见文件的文件 ID（从对话上下文中获取）",
      "type": "string"
    }
  },
  "required": ["query"]
}
```

- 论文文件和审稿意见文件各自单独调用一次，`query` 每次只填一个文件 ID。
- 用户直接在对话中粘贴的审稿意见直接使用，无需调用。
- 无法判断哪个文件是审稿意见时，问用户，不要猜测。
- 无文件 ID 时请用户重新上传；获取后逐条核对意见与论文原文，只引用核实过的章节、表格、数值，不编造证据。

## 工作流

### 1. 意见分诊

对每条意见标记级别：

| 级别 | 含义 | 投入 |
|---|---|---|
| 红 | 决定评分的核心顾虑 | ~60% 篇幅，给证据 |
| 橙 | 可解决的顾虑 | ~30%，给数据或修改 |
| 灰 | 次要问题 | ~10%，一句确认已改 |

多位审稿人共同提出的顾虑合并为"共性问题"优先回复——这几乎一定是真实薄弱点。

### 2. 逐条起草

每项顾虑用三段式：

1. **确认理解**：一句话表明理解了顾虑。
2. **正面回应**：先结论后证据；能用新实验/表格就不用长篇解释；已在论文中的内容要重述而不只写"见第 3.2 节"。
3. **说明修改**：指明修订稿中的位置（章节/表格），建议以颜色标出。

顾虑类型速查：误解→引用位置澄清并重述；缺实验/基线→补充对比或解释为何不适用；表述不清→承认并给出修改后文字；主观批评（如"创新性有限"）→用证据重新界定，缩小并强化论断。

### 3. 输出骨架

```markdown
# 答辩回复：[论文标题]

（一句感谢）

## 共性问题
[多位审稿人顾虑的合并回复]

## 回复审稿人 N
**[级别] [解决方案导向的标题]**
[确认理解 → 回应 → 修改说明]
...

## 新实验汇总（如有）
| 实验 | 回应的问题 | 结果 | 位置 |
```

按红色 → 橙色 → 灰色排序回复，不按审稿人原始顺序。

## 关键原则

- 回复自洽完整：AC 可能不重读论文，关键内容要在回复中重述；核心论点写成支持者可直接引用的形式。
- 写"我们同意"不写"我们承认"；用"修订稿"不用"最终稿"。
- 不引入论文中没有的新论断，避免新攻击面；不攻击审稿人，可客观指出审稿人之间的矛盾。
- 小问题可以让步，大问题必须用证据取胜。
- 无法完成的实验坦诚说明限制（算力、页数），不要沉默回避。
- 有字数限制时：优先表格、合并相关顾虑、致谢压缩为一句，集中篇幅回应最能改变评分的顾虑。
