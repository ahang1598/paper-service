# 论文审查

一套在投稿前系统审查自己学术论文的方法，包括五方面审查清单、用于检查结构清晰度的反向提纲法、表格质量检查以及答辩准备。

## 核心处理函数

### 论文全文读取

#### 方法定义

**functionName**: `AcademicPaperSearch`

**parameters**:

```json
{
  "type": "object",
  "properties": {
    "query": {
      "description": "用户上传论文的文件 ID，从对话上下文或前置技能结果中获取",
      "type": "string"
    }
  },
  "required": ["query"]
}
```

**type** 为 `file` 时，**value** 必须是文件 ID（从上下文或前置技能结果中获取）。

开始审查前，必须先从对话上文或前置技能结果中找到用户上传论文对应的文件 ID，将其原样作为 `query` 的值，再调用 `AcademicPaperSearch` 获取论文全文。`query` 中不要填论文标题、文件名、关键词、自然语言问题或多个文件 ID。不得仅依据文件名、摘要或用户对论文的描述进行审查。

调用成功后，确认返回内容覆盖论文的主要章节，包括摘要、引言、相关工作、方法、实验、结论和参考文献；再基于获取到的全文执行后续审查。如果上下文中不存在文件 ID，请用户重新上传论文；如果函数未返回完整正文，明确说明缺失范围并重新获取，不要根据不完整内容假设全文结论。

## 何时使用本技能

- 用户希望在投稿前审查或检查论文草稿
- 用户希望获得有关论文质量或完整性的反馈
- 用户希望为潜在的审稿人批评做准备
- 用户提到“审查论文”“检查我的草稿”或“自审”

> 如果用户已经收到审稿意见并需要撰写答辩，请推荐用户用 `paper-rebuttal` 技能。

## 前置条件

开始审查前，确认已完成所有章节，所有论断均有证据支撑，已包含局限性章节，表格已经定稿，并且没有未解决的 `\todo{}` 标记。如有任何一项尚未完成，应先完成写作，再开始审查。

## 完美主义方法

> 力求完美：审查自己的论文，考虑审稿人可能提出的每一个问题，并逐一处理。

对负面审稿意见最好的防御，是彻底的自我审查：

1. **对抗式审查**：像一位严格的审稿人一样阅读自己的论文
2. **寻求导师反馈**：请导师审查——反馈越多越好
3. **处理所有问题**：对于发现的每个潜在弱点，要么修正，要么准备辩护

## 反直觉审查协议

在草稿完成后、最终润色前，按顺序执行以下六个阶段。

### 阶段一：拒稿优先总结

首先以审稿人的语气写下：

```
这篇论文应当被拒稿，因为：
1) ...
2) ...
3) ...
```

暂时不要写优点。这样可以迅速暴露高风险弱点。

### 阶段二：新颖性压力测试

针对核心思路提出以下问题：

> 该子领域一名能力出色的博士生在阅读顶尖相关论文后，能否在一个下午内推导出这个想法？

**修改前后示例：**

- 修改前：“我们提出了一种新颖的注意力机制，实现了卓越的性能。”
- 修改后：“我们证明，将三维注意力按坐标轴分解，可以在重建质量损失不超过 0.3 dB 的情况下，将内存复杂度从 O(N^3) 降至 O(N)（表 2）。”

如果答案“很可能是肯定的”，请采取以下措施之一：

1. 缩小论断的适用范围。
2. 强调并非显而易见的机制或理论依据。
3. 将贡献重点从新颖性话术转向稳健性、效率或实验设置的现实性。

### 阶段三：论断—证据审计

创建一个简短表格：

| 论断 ID | 论断语句 | 证据（表/章节） | 结论 |
|---|---|---|---|
| C1 |  |  | 支持充分 / 支持较弱 / 不支持 |
| C2 |  |  | 支持充分 / 支持较弱 / 不支持 |

- `不支持`：立即删除或重写该论断，不要勉强辩护。
- `支持较弱`：弱化措辞、添加限定条件并补充证据。

### 阶段四：可信度评分

以下每项按 0–2 分评分：

- 基线比较的公平性
- 可复现性细节
- 对局限性的坦诚说明
- 失败案例的透明度
- 统计严谨性

如果总分低于 `7/10`，即使主要指标看起来很强，也暂时不要投稿。增益略低但公平性和可复现性更高的论文，往往更容易获得信任。

### 阶段五：熔断条件

出现以下任一情况时，触发“不得投稿”决定：

1. 摘要或引言中超过 20% 的论断缺乏支持。
2. 至少缺少一项明显应纳入的近期基线，且没有解释原因。
3. 核心贡献没有直接的消融实验。
4. 主要增益仅出现在简单子集上。

领域特定的典型熔断信号：

| 领域 | 典型熔断信号 |
|---|---|
| NLP | 准确率/F1 增益低于 0.5%，且未进行统计显著性检验；缺少核心基线（如 GPT-4） |
| 系统 | 增加复杂度后吞吐量增益低于 5%；没有延迟或内存比较 |

### 阶段六：预答辩草稿

在投稿前，针对“新颖性有限”“缺少基线”“不够稳健”“动机不明确”等可能的质疑，各起草一句话回复。提前撰写预答辩可以暴露叙事和证据缺口，改善论文结构并减少审稿结果带来的意外。

最后，将一项有实际意义的局限性从隐藏笔记移入论文；透明度通常会增强审稿人的信心。

## 五方面自审清单

需要快速筛查时，用约 15 分钟仅检查标记为**快速审查**的项目；最终投稿前预留至少 60 分钟，逐项完成全部检查。

### 方面一：贡献充分性

> 核心问题：这篇论文是否为读者提供了新知识？

**新颖性**

- [ ] **（快速审查）** 核心思路是否真正新颖，而不是现有思路的直接组合？
- [ ] 如果以先前工作为基础，扩展是否足够重要？
- [ ] 领域专家是否能轻易想到这一解决方案？
- [ ] 论文是否提供了新的见解或认识，而不仅仅是一种新方法？

**失败案例**

- [ ] 失败案例在实践中是否常见？
- [ ] 目标读者是否会频繁遇到该方法失效的场景？
- [ ] 是否坦诚讨论了失败案例？

**技术成熟度**

- [ ] 核心技术以前是否已经得到广泛研究？
- [ ] 如果该技术已为人所知，论文是否提供了新视角或显著改进？
- [ ] 该改进是否令人意外，还是可以预见？

**贡献范围**

- [ ] 所声称的贡献是否与论文实际实现的内容一致？
- [ ] 每项贡献是否都能通过论文内容进行验证？
- [ ] 每项贡献是否都提供了具体的技术价值，而不只是“我们提出了……”？

**危险信号**：如果核心思路只是直接组合、技术早已成熟且改进可预见，或贡献无法由正文验证，请强化贡献叙事或增加技术深度。

### 方面二：写作清晰度

> 核心问题：读者能否理解并复现该方法？

**可复现性**

- [ ] **（快速审查）** 是否说明了所有模型架构（层、维度、激活函数）？
- [ ] 是否提供了训练细节（优化器、学习率、批量大小、训练轮数）？
- [ ] 是否描述了数据预处理步骤？
- [ ] 是否明确定义了评估协议？
- [ ] 是否必须发布代码才能实现复现？如果是，是否计划发布？

**方法清晰度**

- [ ] **（快速审查）** 每个方法模块是否都有清晰的动机说明，不仅说明“做什么”，还解释“为什么”？
- [ ] 是否描述了每个模块的前向过程（输入 → 步骤 → 输出）？
- [ ] 是否解释了每项设计选择的技术优势？
- [ ] 方法概述是否清晰（问题设置 → 核心贡献 → 章节路线图）？

**结构与语言**

- [ ] 每个段落是否只传达一项信息，且首句陈述主题？
- [ ] 段落之间和章节之间的逻辑是否连贯、过渡是否明确？
- [ ] 全文使用的术语是否一致？
- [ ] 所有符号和记号是否都在使用前定义？
- [ ] 行文是否简洁、语法是否正确？

**危险信号**：如果可复现性存疑，请补充实现细节或补充材料。

### 方面三：实验结果质量

> 核心问题：实验结果是否有说服力？

**定量结果**

- [ ] **（快速审查）** 相较于基线的提升是否显著，而不是处于噪声范围内？
- [ ] 是否提供了标准差或置信区间？
- [ ] 即使优于基线，绝对性能水平是否满足应用要求？
- [ ] 结果是否在所有数据集上均成立，而不是仅在特定数据集上成立？

**结果透明度**

- [ ] 是否展示了失败案例以建立信任？

**效率**

- [ ] 是否比较了计算成本（运行时间、FLOPs、内存）？
- [ ] 是否讨论了质量与效率之间的权衡？
- [ ] 是否报告了实际资源需求（GPU 内存、训练时间）？

**危险信号**：如果改进幅度有限，请强调其他优势（速度、泛化性、简洁性），或增加更具挑战性的测试案例。

### 方面四：实验测试完整性

> 核心问题：是否测试了所有论断？

**消融实验**

- [ ] **（快速审查）** 每项声称的贡献是否都进行了消融实验？
- [ ] 是否有完整的消融表（完整模型与分别移除各组件的模型进行比较）？
- [ ] 是否有针对设计选择和超参数的专项表格？
- [ ] 消融结果是否与论文对各组件的论断一致？

**基线**

- [ ] **（快速审查）** 是否将当前 SOTA 方法纳入基线？
- [ ] 是否包含近 2–3 年的方法以及经典或奠基性方法？
- [ ] 比较是否公平（使用相同的数据、指标和协议）？

**指标与数据集**

- [ ] 是否报告了该任务的所有标准指标？
- [ ] 指标是否适合衡量论文所声称的改进？
- [ ] 是否包含用户研究（如适用）？
- [ ] 是否使用标准基准以便比较？
- [ ] 是否包含具有挑战性且多样化的数据集？
- [ ] 数据集是否真正检验了方法的优势并揭示了其弱点？

**危险信号**：缺少消融实验或基线，是最常见的拒稿原因之一。

### 方面五：方法设计问题

> 核心问题：该方法是否可靠？

**实验设置的有效性**

- [ ] **（快速审查）** 对预期使用场景所作的假设是否现实？
- [ ] 输入数据在实践中是否可以获得？
- [ ] 计算需求是否切合实际？
- [ ] 用户是否真的会按文中描述的方式使用该方法？

**技术可靠性**

- [ ] 该方法是否有理论动机，而不只是经验依据？
- [ ] 是否存在已知的失败模式？是否已经处理？
- [ ] 该方法能否妥善处理边界情况？

**稳健性**

- [ ] 该方法能否使用默认超参数处理不同场景或案例？
- [ ] 是否需要针对每个场景调参？如果需要，这是一个重大弱点。
- [ ] 该方法对输入质量有多敏感？
- [ ] 该方法在训练期间是否稳定？

**收益与成本**

- [ ] **（快速审查）** 新模块的收益是否超过其引入的局限？
- [ ] 性能提升是否足以证明增加复杂度是合理的？
- [ ] 是否有更简单的替代方案能够取得相近结果？

**危险信号**：如果方法需要针对不同场景进行大量调参，请增加稳健性实验，或承认并处理这一局限。

完成五方面检查后，从审稿人视角回答七个总体问题：论文的重要性、新颖性、可靠性、清晰度、完整性、局限性透明度和可复现性是否均达到投稿要求？

## 重要提醒：论断必须有依据

> 论文中的每项论断（尤其是摘要和引言中的论断）都必须正确，并得到实验支持。有些审稿人会因为论断缺乏支持而直接拒稿。

逐一检查摘要和引言中的每项论断。对于每项论断：

- [ ] 它在事实上是否正确？
- [ ] 是否有实验或分析支持它？
- [ ] 是否清楚地引用了支撑该论断的实验？

缺乏支持的论断——尤其是摘要或引言中的论断——可能成为拒稿理由。

## 反向提纲法

> 从已完成的段落中提取写作提纲，并检查行文是否流畅。

完成一个章节（或整篇论文）后：

1. **逐段阅读**，一次只读一个段落
2. **写下每段的主要信息**，每段用一句话概括
3. **阅读这些信息的序列**——逻辑是否连贯？
4. **找出断点**：哪些地方的衔接显得突兀或不合逻辑？
5. **修正**：重新组织段落，添加过渡语句，或拆分、合并段落

将该方法应用于：

- 引言（检查叙事逻辑）
- 方法（检查各模块是否按合理顺序呈现）
- 实验（检查结果是否按有意义的顺序呈现）

## 表格质量检查清单

- [ ] 表注位于表格上方
- [ ] 不使用竖线
- [ ] 使用 booktabs（`\toprule`、`\midrule`、`\bottomrule`）
- [ ] 突出显示最佳结果（粗体或颜色）
- [ ] 标明指标方向（↑/↓）
- [ ] 表注描述实验设置或符号，而不是结果
- [ ] 正文中引用了所有表格

---

## 结论与局限性检查

- [ ] 结论总结了贡献和关键结果
- [ ] **包含局限性章节**（审稿人经常指出其缺失）
- [ ] 局限性应涉及任务或实验设置的适用范围（类似未来工作），而不是技术缺陷
  > 规则：“如果我们的方法在 SOTA 指标上没有落后，就不属于技术缺陷。”
- [ ] 对局限性的陈述要坦诚，但不要自我否定

---

## 投稿前最终检查

- [ ] 所有参考文献均完整（没有“?”或缺失条目）
- [ ] 作者信息符合投稿场所的要求
- [ ] 页数在限制范围内
- [ ] 补充材料得到恰当引用
- [ ] 论文中没有遗留 TODO 标记
- [ ] 致谢部分内容恰当
- [ ] 没有意外违反双盲审稿要求（匿名评审时）
- [ ] 所有引用文献都有完整的书目信息（作者、标题、发表场所、年份）
- [ ] 没有破坏匿名性的自引（双盲评审时）
- [ ] 已引用关键相关工作——遗漏一篇重要基线论文可能导致拒稿
